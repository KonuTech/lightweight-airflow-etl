<objective>
Stand up the full local docker-compose stack (Oracle Database Free + Airflow metadata Postgres +
Airflow LocalExecutor services) end-to-end, with the admin/admin credential pair working against
both Oracle and Airflow's REST API, and one Oracle table verified to exist via Oracle's own
metadata views — not just DDL exit status. This is the phase's tracer: the thinnest slice that
touches every layer (compose orchestration, Oracle DDL delivery, Airflow auth provisioning, and a
host-side verification tool), proving the architecture before Plan 01-02/03/04 expand it.

Purpose: Prove the hardest, riskiest parts of this phase — Oracle's two-directory init-script
mount point and CDB$ROOT/FREEPDB1 session context (RESEARCH.md's correction to CONTEXT.md D-06),
and Airflow 3's simple_auth_manager non-interactive admin/admin provisioning (D-10) — actually work
together in one running stack, before expanding to the full 5-table schema and custom image.

Note on credential surface (assumption-delta check): this phase introduces multiple underlying
auth mechanisms — Oracle's SYS/SYSTEM account (ORACLE_PASSWORD), Oracle's dedicated APP_USER
account (ORACLE_APP_USER_PASSWORD), and Airflow's simple_auth_manager user — all sharing the same
literal "admin"/"admin" value. Resolution: **add-alongside**, not promote. The `.env`-sourced
"admin"/"admin" value is the single source of truth (INFRA-03's actual noun); the three
mechanisms that read it stay separate, uncollapsed accounts (per D-07's dedicated-schema
rationale) — there is no single account to "promote" to primary. This was already resolved by
CONTEXT.md D-07/D-09 and RESEARCH.md's Assumption A2; recorded here for traceability, not reopened.

Output: A running `docker compose up -d --wait` stack, `scripts/verify_environment.py` passing,
and the package-legitimacy review for this phase's three flagged PyPI installs completed.
</objective>

## Flagged Assumptions (Unresolved Edge-Probe Items)

These items were surfaced by the spec-less edge-probe fallback (no SPEC.md exists for this
phase) and could not be resolved during planning. They are recorded here as explicit, carried-forward
assumptions — not silently dropped, and no resolution is fabricated.

- **INFRA-01 (category: unclassified — the deterministic probe could not auto-classify this
  infra-shaped requirement).** The exact readiness/startup-ordering interleaving across all three
  service tiers (Oracle, Airflow's metadata Postgres, the four Airflow runtime services) is
  assumed to be adequately handled by docker-compose's `depends_on: condition: service_healthy`
  gates. This specific race window was not exhaustively probed beyond one clean-boot run. If a
  race is ever observed in practice (e.g. an Airflow service starting before Oracle's healthcheck
  passes because a `depends_on` clause was mis-typed), treat it as a real bug to fix, not an
  accepted edge case.

- **INFRA-03 (category: concurrency — "If interrupted or run in parallel, what is guaranteed?").**
  It is unverified what happens if two `docker compose up` invocations run concurrently against
  the same not-yet-initialized named volumes (e.g. a stray double-invocation of `make up`).
  RESEARCH.md's empirical confirmation of admin/admin provisioning covered only a single clean
  boot from an ephemeral volume — not a race between two simultaneous first-boot sequences for
  Oracle's `APP_USER` creation or the `simple_auth_manager` password-file seed. No safety
  guarantee is asserted here; this is flagged for developer awareness, not resolved.
</flagged_assumptions>
