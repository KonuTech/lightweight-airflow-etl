<objective>
Land the DB-level PK/index/trigger DDL (D-13–D-19): `PRIMARY KEY` on each `_valid` table's own id
column, a plain index on `orders_valid.customer_id` for the JOIN workload, and a `BEFORE INSERT`
trigger on `orders_valid` that validates `customer_id` exists in `customers_valid` — a DB-level
safety net on top of the Python-side correlation Plan 07-01 already guarantees, never a replacement
for it.

Purpose: Catches any future generator regression as a load failure instead of silent bad data
(D-14's explicit reasoning) — but this DDL is genuinely irreversible against existing data (D-14's
own `one-way` rating: undoing it requires a DDL migration and, practically, the exact `make reset`
this plan itself performs), so this plan pauses for explicit confirmation before applying it.
Output: `docker/oracle/init/05_correlation_constraints.sql`, live proof via
`tests/integration/test_correlation_constraints.py`.
</objective>

## Planner Decision (resolves RESEARCH.md Open Question 3 / Assumption A3 — the redundant-index question)

`ALTER TABLE customers_valid ADD CONSTRAINT pk_customers_valid PRIMARY KEY (customer_id)` already
creates an implicit unique index on `customers_valid.customer_id` — D-13's "plain index on
customer_id in both tables" is satisfied on the `customers_valid` side BY the PK's own implicit
index; adding a second, explicit, redundant index there would provide zero additional query
capability. The explicit, NEW index this plan adds is scoped to `orders_valid.customer_id` only
(the FK/join side, which has no PK-implied index of its own — its PK is on `order_id`, a different
column). This is the concrete resolution D-13's literal "both" wording left ambiguous.
</planner_decisions>
