<objective>
Fix the Critical silent-data-loss regression `03-REVIEW.md` found in plan 03-06's own CR-02 fix:
`source.py`'s `_filtered_rows()` currently trusts `detect_header()`'s `footer_row_indices`/
`repeated_header_row_indices` as absolute truth, but those indices are computed from only a 64 KiB
HEAD SAMPLE (`source.SAMPLE_BYTES`) of the file. On any file larger than that sample, the row whose
bytes straddle the sample's byte-65536 cutoff is truncated mid-row *within the sample only* —
`detect_header()`'s footer-scoring walk sees a malformed field count for that truncated copy and
flags its absolute index as "footer" or "repeated-header", even though the SAME row, read in full
from the real file, is a perfectly well-formed data row. `_filtered_rows()` then silently drops that
real row from PASS 2's real, complete read: no `invalid_rows` entry, no exception, no count
mismatch surfaced anywhere — reproduced empirically by `03-REVIEW.md` as a clean 6,000-row
(~117 KiB) CSV losing exactly 1 row (`ID003276`) with `process_chunks()` reporting `valid: 5999` for
a 6,000-row input.

The fix (03-REVIEW.md's option (a)): re-validate every sample-derived candidate exclusion against
the REAL, full-file row content in PASS 2, before actually excluding it. A candidate index is only
excluded if the real row at that index independently satisfies the same criterion `detect_header()`
itself would apply (this module never passes `footer_patterns`/`skip_footer_rows` to
`detect_header()`, so its only footer criterion here is a field-count mismatch): real field count
differs from the header's, or real values exactly equal the header's own values (repeated-header).
A row whose real content actually matches the header — proving the sample-derived flag was a
truncation artifact, not a genuine footer/repeat — passes through untouched. This closes the
false-positive exclusion (data loss) without reopening G-03-2 (a genuine, small, within-sample
preamble/footer/repeated-header row must still be excluded, since its real content still fails the
same re-validated criterion).

Out of scope (unchanged, pre-existing, accepted limitation per 03-06's own T-03-10): a genuine
footer/repeated-header row physically beyond the 64 KiB sample boundary in a very large file is
still never detected/excluded at all — this is a false NEGATIVE (safe: the row is simply treated as
ordinary data, which the caller's own `WRONG_COLUMN_COUNT` check may still flag if it's a real
footer, or which prints as data if not), not the false-POSITIVE data-loss bug this plan fixes.
Extending footer detection to see the whole file would require reading a tail-window of the file
(an architectural change 03-REVIEW.md itself scoped as "the more complete fix", explicitly not
required here) and would conflict with ENGINE-07's bounded-memory, detect-once-per-file design —
not built in this gap-closure plan.

Purpose: `03-06`'s CR-02 fix wired `detect_header()`'s footer/repeated-header indices into PASS 2's
real read for the first time — but did so by trusting those sample-derived indices unconditionally,
introducing a NEW, worse bug (invisible data loss on ordinary large files) than the one it fixed
(a false-inclusion of a footer row, which was at least visible in row counts). This plan closes that
regression before Phase 4 builds Oracle bulk-loading on top of `process_chunks()`'s row counts.
Output: `source.py`'s `_filtered_rows()` re-validates every candidate exclusion against real
full-file row content; two new regression tests prove both the fix (no data loss on a >64 KiB
well-formed file) and no regression of G-03-2 (an in-sample repeated-header row is still excluded,
even inside a file whose total size exceeds the sample).
</objective>
