<assumption_delta_decision>
D-31 widens `file_pattern` from a singular plain-CSV glob (`"customers_*.csv"`) to a plural one that
matches both plain and compressed variants (`"customers_*.csv*"`). Resolution: the widened glob
REPLACES the old value in place (promote, not add-alongside) — there is exactly one `file_pattern`
field per dataset, and `"customers_*.csv*"` already matches every filename `"customers_*.csv"` used
to match (a `*` glob segment matches zero-or-more characters, so `"customers_20260829.csv"` still
matches `"customers_*.csv*"`) plus the new `.gz`/`.zip` cases. No second field, no dual-pattern list —
this is a strict widening of the existing contract, not a new parallel one.
</assumption_delta_decision>

<objective>
Deliver the two pieces of Phase 3 scope that are genuinely independent of the Python
`csv_processor` engine itself: the Oracle `_INVALID` table DDL migration discovered during
`/gsd-discuss-phase` (D-01 through D-08), and the `file_pattern` widening discovered as its own
follow-up (D-31). Per D-02, this migration runs NOW, in Phase 3, even though Phase 3 itself never
inserts into Oracle (that's Phase 4) — the schema gap gets fixed as soon as discovered rather than
carried forward. Neither requires any of `csv_processor`'s new detect/validate/normalize/engine
code to exist first, so this plan runs fully in parallel with 03-02's dependency/vendoring work.

Purpose: unblocks Phase 4's future Oracle inserts against invalid rows that carry raw string values
(not just typed values) in NOT NULL/typed columns that structurally cannot hold them today, and
gives Phase 5's future file-sensor a glob that already covers compressed input per D-29's "read
compressed CSV transparently" requirement.
Output: `docker/oracle/init/04_widen_invalid_columns.sql`, a `verify_widened_invalid_columns()`
addition to `scripts/verify_environment.py`, and updated `file_pattern` values in both real dataset
configs.
</objective>
