<objective>
Close `03-REVIEW.md`'s new Critical finding (this gap-closure round's CR-04): a genuinely malformed
data row that happens to land at the exact position `detect_header()`'s sample-bounded footer-scoring
walk treats as the sample's own tail is silently dropped from `process_chunks()`'s output — absent
from both `valid_rows` and `invalid_rows` — instead of surfacing as an ordinary `WRONG_COLUMN_COUNT`
invalid row.

Root cause: `detect/header.py`'s `_detect_footer_rows` (lines 207-256) always walks BACKWARD starting
from the LAST row of whatever `data_rows` sequence it is given, including every contiguous row whose
field count differs from the header's, and stopping at the first well-formed row it hits. `source.py`
calls `detect_header()` with only the bounded 64 KiB `sample_rows` (`prepare_source()`, ~line 284), so
for any file larger than `SAMPLE_BYTES`, "the last row of `data_rows`" is the sample's own arbitrary
truncation cutoff — an essentially arbitrary interior position in the real file — never the file's
true tail. 03-07's own CR-03 fix re-validates every sample-derived candidate exclusion against the
REAL row content using the SAME criterion `engine.py` uses to classify `WRONG_COLUMN_COUNT`
(`len(row) != header_field_count`) or repeated-header (`tuple(row) == raw_header`). This closed the
prior round's "well-formed row wrongly excluded due to sample truncation" bug, but cannot distinguish
that case from a genuinely malformed row landing at the same sample-tail position: both independently
satisfy the identical re-validated criterion against their own (for a non-boundary row, sample content
== real content) content, so CR-03's re-validation trivially "confirms" the malformed row's exclusion
too. Reproduced in `03-REVIEW.md`: a ~125 KB, 2-column file with one genuinely malformed row at data
row 3277 (one field instead of two) yields `process_chunks()` reporting `6277 valid / 0 invalid` for
6278 real data rows — the malformed row vanishes with zero trace.

The fix (structural, per this round's own required approach — NOT another content-re-derivation
layer): bound WHICH sample-derived candidate indices are even eligible for exclusion consideration by
the sample's OWN provable byte coverage, before any content check runs at all. `prepare_source()`
computes `sample_was_truncated = len(sample) == SAMPLE_BYTES` (true whenever there is more file beyond
what PASS 1 read) and `sample_covered_row_count` — the count of rows the sample bytes actually read
PROVE were captured in full: every row `csv.reader` parsed from the sample except possibly the very
last one, when truncated (that last row's true completeness can never be proven from a truncated
sample alone — it may be a genuine, complete row that merely ends near the cutoff, or a truncated
fragment; either way, it cannot be trusted as the file's real tail). `_filtered_rows()` gains this as a
new required parameter and only treats a sample-derived candidate as eligible for exclusion at all
when its absolute index is strictly less than `sample_covered_row_count` — CR-03's existing content
re-validation (`is_footer_shaped`/`is_repeated_header`) still runs on top of this new gate, unchanged,
for every row that IS eligible. This closes CR-04's exact reproduction (the malformed row is always
the sample's own last parsed row, so it is always ineligible under the new gate whenever the sample
was truncated) while fully preserving G-03-2 (a genuine, small, within-sample preamble/footer/
repeated-header row's absolute index is always strictly less than `sample_covered_row_count`, since it
is never the sample's last row in a file that fits entirely inside the sample, or it is well within
the provably-covered prefix of a larger file) and CR-03 (the row whose bytes straddle the sample
cutoff is now excluded from candidacy by the coverage gate itself, making the content re-validation
that previously saved it redundant-but-harmless for that specific row).

Documented residual (accepted, not fixed by this round, per the reviewer's own "Option 2: complete
fix" being explicitly out of scope): if MULTIPLE consecutive genuinely-malformed rows land exactly at
the sample's truncation boundary (rather than the single row this plan's regression test reproduces),
every one of them except the very last would remain "within coverage" and could still be
misclassified as footer-shaped by CR-03's content check alone. Eliminating this fully would require
buffering a real look-ahead window during PASS 2's streaming read (finalizing "these are footer rows"
only once EOF is truly reached) — an architectural change RESEARCH.md and `03-REVIEW.md` both already
scoped as a separate, larger effort, not required by this round's own gap-closure scope.

Purpose: Phase 4's Oracle bulk-loading builds directly on `process_chunks()`'s row counts and
per-row error classification — a third silent-data-loss bug on the exact same code path (after
03-06/CR-02 and 03-07/CR-03) must be closed with a change to the exclusion mechanism's own eligibility
rule, not another point patch, before that dependency is built.
Output: `source.py`'s `_filtered_rows()` gains a provable-sample-coverage eligibility gate ahead of its
existing content re-validation; two new regression tests prove the CR-04 reproduction is fixed and
that G-03-2's exclusion guarantee coexists correctly with it in the same file.
</objective>
