<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Local developer machine ↔ `docker compose exec` subprocess call | `scripts/verify_environment.py` shells out from the developer's own host process into a running container; invoked only locally via `make verify`/`make verify-phase8`, never over a network |
| Verification script output ↔ terminal/CI log | New checks print fixed `OK:`/`FAILED:` strings; no secrets are read or interpolated into the exec'd Python code |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-08-05 | Tampering / Denial of Service | `verify_data_write_access()`'s write-then-delete probe file | mitigate | Use a dotfile name (`.verify_write_probe`) that can never match `customers_*.csv*`/`orders_*.csv*` glob patterns, and wrap the delete in `try/finally` so the probe is always removed even if the content assertion fails — never leaves a stray file that could confuse `csv_ingest`'s `FileSensor`. |
| T-08-06 | Information Disclosure | Subprocess command strings / captured stdout-stderr | accept | The exec'd Python code contains no secrets — only fixed dataset names (`customers`/`orders`) and a static import statement. Documented here as a discipline for any future `_docker_compose_exec()`-based check, not a fix needed on this pass. |
| T-08-07 | Elevation of Privilege | `docker compose exec` subprocess invoked by `verify_environment.py` | accept | Runs with the invoking developer's own local Docker permissions, not elevated — equivalent to the existing `Makefile`'s own `verify-phase5` precedent, which already execs into a container the same way. |

</threat_model>
