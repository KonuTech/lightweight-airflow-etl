<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `generate_task` (Airflow worker) ↔ subprocess (`generator/generate_csv.py`) | Worker process spawns a subprocess with an argument list built from Airflow `Param`-validated/`logical_date`-derived values |
| `summary_task` (Airflow worker) ↔ Oracle `ingestion_metadata` table | Read-only query, bind-parameterized |
| `retention_task` (Airflow worker) ↔ local filesystem `data/{customers,orders}/` | File deletion under a fixed, hardcoded root |
| Parent DAG (`csv_generate_schedule`) ↔ triggered child DAGs (`csv_ingest`, `report_ready`) | `conf=` payload crossing a DAG-to-DAG trigger boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-9-01 | Tampering | `summary_task`'s `ingestion_metadata` query | mitigate | `cursor.execute(_LATEST_INGESTION_SQL, dataset=dataset)` uses `oracledb`'s native bind-parameter substitution; `dataset` itself is a hardcoded literal from a fixed `for` loop over `("customers", "orders")`, never external input -- no injection surface. |
| T-9-02 | Tampering | `retention_task`'s file deletion | mitigate | `retention_sweep()` (Plan 09-01) is only ever called here with `paths.DATA_ROOT / dataset` -- a fixed, hardcoded root -- and its own internal glob pattern (`{dataset}_*.csv*`) is likewise fixed; it never constructs a path from unsanitized external input, so no `resolve_safe_config_path()`-style traversal guarding is needed. |
| T-9-03 | Tampering | `generate_task`'s `subprocess.run([...])` argument list | mitigate | All arguments are hardcoded literals (`"--correlated"`, `"--compress"`) or `str()`-cast values already validated by Airflow's own Param JSON-Schema (`rows`: `type="integer", minimum=1`; `invalid_ratio`: `type="number", minimum=0.0, maximum=1.0`) or derived from `logical_date` (Airflow-controlled, not user-supplied). List-form `subprocess.run([...])` with no `shell=True` prevents shell injection by construction, matching this codebase's existing convention. |
| T-9-04 | Spoofing | `trigger_customers`/`trigger_orders`'s `conf=` payload reaching `csv_ingest` | accept | `conf=` is a hardcoded dict literal in this DAG's own source, never derived from runtime input -- no spoofing surface at this integration point. `csv_ingest.py`'s own `load_config_task` still independently re-validates `dataset`/`config_path` per its own existing defense-in-depth convention, unchanged by this plan. |
| T-9-05 | Denial of Service | A stuck/hung chain-trigger cascade holding the Triggerer or blocking the next hourly cycle indefinitely | mitigate | `dagrun_timeout=timedelta(minutes=45)` (D-10) bounds the entire cascade; `max_active_runs=1` (SCHED-04) queues rather than races an overlapping cycle; `retries=0` (D-09) on every task ensures no silent retry storm. |
| T-9-06 | Repudiation | No dedicated audit/correlation ID linking a specific hourly run to its `ingestion_metadata` rows | accept | Out of scope this milestone -- `ingestion_metadata`'s existing `checksum`+`processed_at` columns already provide sufficient traceability at this project's scale; not requested in CONTEXT.md. |

</threat_model>
