## Planner Decision (resolves RESEARCH.md Open Question 2)

The sensor's "has data for the current partition" check queries `ingestion_metadata` (NOT
`customers_valid`/`orders_valid` directly) — following D-28's literal wording. `ingestion_metadata`
is not itself partitioned and carries a `dataset` column and a `processed_at` timestamp, making the
"both present" check a single `SELECT COUNT(DISTINCT dataset) FROM ingestion_metadata WHERE dataset
IN ('customers', 'orders') AND TRUNC(processed_at) = TRUNC(SYSDATE)` query — simpler than querying
two separately-interval-partitioned data tables, and D-28's own wording already specifies this
table.
</planner_decisions>

| Triggerer (async event loop) -> Oracle | The new custom trigger runs inside Airflow's shared triggerer process, polling Oracle over the network (container-internal) |
| Report task -> Oracle | A normal worker-process task querying Oracle with the existing admin/admin dev credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-03-01 | Denial of Service | `OraclePartitionReadyTrigger.run()`'s Oracle polling loop | high | mitigate | MUST use `oracledb.connect_async()`, never blocking `connect()` — a blocking call inside `async def run()` stalls the triggerer's single shared event loop for every other deferred task project-wide (existing `wait_for_file` sensors included), a real availability risk specific to this new code. Task 1's acceptance criteria requires this; Task 1's unit test mocks `connect_async` specifically (not a sync `connect`), so a regression to a blocking call would be caught by import/type mismatch during review |
