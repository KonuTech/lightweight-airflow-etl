## Planner Decisions (resolving RESEARCH.md's open questions explicitly — not left ambiguous)

**PD-1 (resolves RESEARCH.md Pitfall 1 / Open Question 1 — RNG-continuation semantics):**
`generate_rows()` gains three new **optional, keyword-only** parameters: `rng: random.Random | None
= None`, `fake: Faker | None = None`, `customer_id_pool: list[str] | None = None`. When `rng`/`fake`
are `None` (every EXISTING caller — fully backward compatible), the function constructs them
internally exactly as today. `generate_correlated_datasets()` constructs ONE `rng`/`fake` pair and
passes the SAME live objects into both the customers call and the orders call — this is literal
object-identity continuation across the customers→orders boundary, satisfying D-05's "the
pool-sampling/Zipf RNG draws from the same seeded `random.Random(seed)` **instance**" by its most
literal reading.

**PD-2 (resolves the `customer_id_pool` dispatch, and RESEARCH.md Pitfall 2's assumed breakage):**
When a config declares a `customer_id` column: `customer_id_pool=None` (the default — used for
`customers_config`, which OWNS customer identity) assigns sequential structured IDs
(`CUST-{hash}-000001`, `000002`, ...). `customer_id_pool=<non-empty list>` (used ONLY by
`generate_correlated_datasets()` for `orders_config`) assigns Zipf-weighted pool samples instead.
This means a bare `generate_rows(orders_config, ...)` call with no pool still runs deterministically
(sequential IDs, not correlated) rather than raising — RESEARCH.md's Pitfall 2 assumed a
hard-required-pool design that would break these call sites structurally; this design does not, so
`tests/unit/test_generate_csv.py`'s five EXISTING `generate_rows(orders_config, ...)`-level tests
(lines ~194-253, asserting determinism/header/category-applicability/decimal-places — never
`customer_id` *content*) remain valid and are NOT modified by this plan. The two call sites that
DO need updating are the CLI-level ones (`generate_csv.main(["--dataset", "orders", ...])`), because
D-22 blocks that CLI path entirely — that remediation is Plan 07-02's job, not this plan's, since
the CLI's `--correlated` flag does not exist until 07-02.

**D-04's empty-pool check** lives in `generate_correlated_datasets()` itself, checked immediately
after generating customers and extracting the valid-customer pool, before ever calling
`generate_rows()` for orders — not inside `generate_rows()`'s own dispatch (which only rejects an
explicitly-provided-but-empty `customer_id_pool` list, a defense-in-depth mirror of the same check).
</planner_decisions>
