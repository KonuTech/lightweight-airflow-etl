<objective>
Build the Oracle bulk-load primitives (`csv_processor.load`) and the shared result models
(`csv_processor.models`) that Plan 04-02's `process()` entrypoint will assemble, and prove
them end-to-end against the real, running Oracle Database Free container -- true
`executemany()` bulk inserts into `<DATASET>_VALID`/`<DATASET>_INVALID`, one
`ingestion_metadata` row per file, and a checksum-based idempotency guard, per LOAD-01
through LOAD-04. Also closes a genuine SQL-injection-via-identifier gap in Phase 2's
already-existing `csv_processor.config.models` (`OracleTargetSpec.valid_table`/
`invalid_table` and `ColumnSpec.name` had no format constraint before this plan, despite
being interpolated directly into dynamically-built INSERT statements).

Purpose: Oracle has no bind-parameter mechanism for table/column identifiers -- only values
bind safely. Every dynamically-built INSERT statement in this project depends on the
identifiers it's built from being provably safe, and every later phase (5, 6) depends on
`load.py`'s primitives already being proven against a real database, not mocks (TEST-02).

Output: `csv_processor.models.{Status, ProcessingResult}`, `csv_processor.load.{sha256_file,
get_connection, insert_rows, find_existing_ingestion, record_ingestion}`, an
`OracleTargetSpec`/`ColumnSpec` identifier-allowlist validator, and a real-Oracle integration
test suite (`tests/integration/`) proving LOAD-01/02/03/04.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| config.json -> dynamically-built SQL | `oracle.valid_table`/`invalid_table` and every `columns[].name` are developer-authored config values that get interpolated directly into `INSERT` statement identifiers -- Oracle has no bind-parameter mechanism for identifiers, only values, so this string-formatting step is the only place an injection-shaped identifier could reach a live SQL statement |
| csv_processor -> Oracle | `load.py`'s executemany() calls are the only write path into `<DATASET>_VALID`/`<DATASET>_INVALID`/`ingestion_metadata`; row VALUES are always bind-parameter-safe (never interpolated), only table/column NAMES are string-built |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-04-01 | Tampering | `config/models.py`'s `OracleTargetSpec.valid_table`/`invalid_table`, `ColumnSpec.name` -> `load._build_insert_sql`'s string interpolation | high | mitigate | `is_safe_identifier()` regex allowlist (`^[A-Za-z_][A-Za-z0-9_]{0,127}$`) enforced at TWO layers: Pydantic `model_validator` rejects a malformed config at load time (Task 1), AND `load.insert_rows` re-checks every table/column name immediately before building the INSERT string (defense-in-depth against a future caller that bypasses config validation) |
| T-04-02 | Tampering | `load.record_ingestion` -> `ingestion_metadata` | medium | mitigate | Insert-only discipline (no `UPDATE` path exists in `load.py`); a conflicting re-record for the same `(dataset, checksum)` is surfaced via `oracledb.IntegrityError`, never silently applied |
| T-04-03 | Information Disclosure | `load.py`'s exception handling -> stdout/logs | low | accept | This plan's functions never call `print`/`logging` with row contents; genuine Oracle exceptions propagate to the caller (Plan 04-02's `process()`) rather than being logged here -- accepted since there is no logging surface in `load.py` itself to misuse |
| T-04-04 | Denial of Service | Oversized/malformed value -> `executemany()` batch failure | low | accept | A single oversized value raises `oracledb.DatabaseError` for the WHOLE batch (no partial insert, per D-02's atomicity); this is intended fail-closed behavior, not a gap -- `REL-01`'s `batcherrors` defensive layer is explicitly deferred to v2 |

</threat_model>
