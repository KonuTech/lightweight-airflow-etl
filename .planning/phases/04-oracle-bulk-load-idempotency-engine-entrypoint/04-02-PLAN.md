<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `process()`'s ProcessingResult -> future callers (Phase 5's DAG, tests, a future CLI) | The one value that crosses the entrypoint boundary out of `csv_processor` -- must never carry more than aggregate counts/status/checksum/duration |
| `process()` -> Oracle exception surface | `process()` is the sole place that decides which oracledb exceptions are "just a DATABASE_ERROR" vs. the specific IntegrityError/ORA-00001 idempotency-race signal |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-04-05 | Information Disclosure | `process()`'s `ProcessingResult` construction | medium | mitigate | `ProcessingResult` (Plan 04-01's `models.py`, frozen + `extra="forbid"`) has a fixed field list (status/dataset/file_name/total_rows/valid_rows/invalid_rows/duration_seconds/checksum) with no credential or per-row field -- `extra="forbid"` makes it a validation error, not a silent pass, if a future edit ever tried to smuggle a credential field in |
| T-04-06 | Tampering | `oracledb.IntegrityError` misclassification (Pitfall 3) | medium | mitigate | `process()` checks `error_obj.full_code == "ORA-00001"` specifically before treating an `IntegrityError` as the idempotency race -- any other integrity violation (e.g. a genuine data problem) falls through to the generic `DATABASE_ERROR` path, never silently swallowed as "already processed" |
| T-04-07 | Denial of Service | An unexpected exception during `process()` leaves the Oracle connection open | low | mitigate | A `finally` block always calls `connection.close()` regardless of which status path returns |

</threat_model>
