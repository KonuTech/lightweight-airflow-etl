<objective>
Close `03-REVIEW.md`'s new Critical finding (this review round's own **CR-01**, its fourth
consecutive round against `source.py`'s footer/repeated-header row-exclusion logic) and its
**WR-01** Warning, both found while auditing 03-08's own CR-04 fix.

**CR-01 (mandatory, Critical): the coverage gate protects only the single boundary index, not the
full contiguous run.** `detect/header.py`'s `_detect_footer_rows` (lines 240-255, read directly this
session) walks BACKWARD from the last row of whatever `data_rows` it is given and appends **every
contiguous** row whose field count differs from the header's, stopping only at the first (from the
end) row that matches neither criterion (`if not (field_count_differs or pattern_matches): break`).
`source.py` calls `detect_header()` with only the bounded 64 KiB `sample_rows`, so for any file
larger than `SAMPLE_BYTES`, "the last row" is the sample's own arbitrary truncation cutoff. 03-08's
own CR-04 fix added a coverage-eligibility gate (`absolute_index < sample_covered_row_count`) that
correctly protects the SINGLE index equal to `sample_covered_row_count` (the sample's own unprovable
last row) — but every OTHER index in the SAME contiguous backward-walk run (e.g. `sample_covered_row_count
- 1`, `- 2`, ...) remains fully "eligible" under that comparison (since each is numerically `<
sample_covered_row_count`), and is only checked by CR-03's content re-validation. Content re-validation
cannot tell "a genuine footer" from "a genuinely malformed data row that also happens to mismatch the
header's field count" — so when 2+ such rows are chained together at the sample's tail (03-REVIEW.md's
own example: an ordinary trailing blank line immediately adjacent to a genuinely-truncated row — a
blank line trivially mismatches any header's field count too), CR-03's content check "confirms" every
one of them as footer-shaped, and all but the very last are **silently dropped** — the exact
CR-02/CR-04 failure mode recurring one row earlier. No existing test (in this file or 03-08's own new
tests) constructs a contiguous run of 2+ candidates, so this was never caught until this review round.

**Fix (per 03-REVIEW.md's own concrete suggested code, verified self-consistent against `source.py`'s
actual variable semantics — see `<read_first>` note in Task 1 about a paraphrase discrepancy in this
round's own gap-closure framing prose):** extract a small, pure helper,
`_uncoverable_tail_indices(excluded_indices, sample_covered_row_count) -> set[int]`, that walks
backward starting at `idx = sample_covered_row_count` (this IS the sample's own unprovable last row's
absolute index whenever the sample was truncated — `sample_covered_row_count` is a *count* of
provably-covered rows, so index `sample_covered_row_count` itself is the first *uncovered* one) and,
while `idx in excluded_indices`, adds it to the result and decrements — stopping at the first index
NOT in `excluded_indices`. `_filtered_rows()` computes this set ONCE per call (not per row, per
03-REVIEW.md's own explicit guidance) and gates on `absolute_index not in uncoverable_tail` instead of
the prior single-index comparison. A genuine, small, in-sample preamble/footer/repeated-header row
(G-03-2) that does NOT touch the boundary is untouched by this change (the backward walk from
`sample_covered_row_count` never reaches it, since the walk stops at the first gap) and remains
eligible/excluded exactly as before.

**WR-01 (mandatory, folded in since the same file/function is already being touched): `sample_was_truncated`
off-by-one.** `sample_was_truncated = len(sample) == SAMPLE_BYTES` (source.py, `prepare_source()`)
cannot distinguish "the read was cut off because more file follows" from "the file's real size
happens to equal `SAMPLE_BYTES` exactly, and the read simply reached true EOF" — both produce the
identical `len(sample) == SAMPLE_BYTES` result. In the second case this wrongly strips
coverage-eligibility from that file's genuinely complete last row, so a real footer there fails to be
excluded and instead surfaces as a spurious `WRONG_COLUMN_COUNT` invalid row (fails loud, not
silently — lower severity than CR-01, but the identical root cause: inferring truncation from a byte
count alone). Fix: read `SAMPLE_BYTES + 1` bytes instead, and derive `sample_was_truncated` from
whether that extra byte was actually returned (`len(sample) > SAMPLE_BYTES`) — this works uniformly
for compressed and uncompressed streams (both are plain binary file-like objects supporting
`.read(n)`; no stream-type-specific branching needed), then trim `sample` back to `SAMPLE_BYTES`
bytes so every downstream detector (encoding/dialect/`sample_rows` construction) is unaffected.

**Adversarial edge cases considered and closed by this plan (not left for a fifth round):**
- Contiguous run touching absolute index 0 — `_uncoverable_tail_indices`'s backward walk
  self-terminates the moment it hits an index outside `excluded_indices` OR goes negative (a negative
  index can never be a member of a set of non-negative row indices), so no explicit bounds guard is
  needed; still covered by a direct unit test to make this explicit rather than implicit.
- `excluded_indices` empty — the walk's very first membership check fails immediately, returning an
  empty set; no exclusion candidates means no eligibility question to answer at all.
- `sample_covered_row_count == 0` (the sample was truncated almost immediately, e.g. barely past the
  header) — `idx = 0` is checked against `excluded_indices`, which is always constructed from
  `header_row_index + 1`-relative indices (never index 0 itself unless the header is at absolute index
  -1, which cannot happen) — safe by construction, confirmed by a direct unit test rather than assumed.
- `sample_covered_row_count` at or past `len(sample_rows)` (the untruncated case) — the walk starts at
  an out-of-range index that can never be a member of `excluded_indices` (which only ever contains
  real row indices), so the helper correctly imposes zero additional restriction when the whole file
  fit inside the sample — exactly the desired behavior (no truncation, no ambiguity to protect
  against).
- **Genuinely accepted, narrow residual (unchanged from 03-08's own T-03-15, now correctly narrowed):**
  a genuine footer/repeated-header row physically located BEYOND the 64 KiB detection sample in a very
  large file is still never detected/excluded at all (a false negative — safe, since it simply falls
  through to ordinary per-row validation rather than being silently dropped). This is a pre-existing,
  already-accepted limitation of sampling only the file's head, orthogonal to CR-01/WR-01, and remains
  out of scope. IN-03's separate, self-mitigating "header row itself is sample-truncated" case
  (03-REVIEW.md) also remains explicitly out of this round's mandatory scope, per the gap-closure
  brief's own instruction not to dilute focus on WR-02/WR-03/IN-01/IN-02/IN-04.

simultaneously.
