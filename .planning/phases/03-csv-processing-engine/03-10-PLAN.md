<objective>
Close 03-VERIFICATION.md's new gap finding (this report's own re-verification round, distinct from
and unrelated to the 03-06 through 03-09 sample-boundary-truncation chain, which the same report
independently re-confirms stays closed via 187 passing tests) -- coined **FTR-01** in this plan for
traceability, since 03-REVIEW.md's own prior "IN-03" label mischaracterized it as an accepted,
non-actionable Info-level note, a characterization 03-VERIFICATION.md's independent, adversarial
re-check explicitly rejected and scored FAILED against Roadmap Success Criterion #2 and 03-02-PLAN's
own "MUST NOT silently drop a structurally invalid row" prohibition.

**Root cause:** `source.py`'s `prepare_source()` calls `detect/header.py`'s `detect_header()` with
`skip_footer_rows=0`/`footer_patterns=()` for every dataset, unconditionally -- these are not
"footer detection disabled" values, they are simply unset optional hints, so `_detect_footer_rows()`'s
field-count-mismatch heuristic (walk backward from the sample's last row, flag every contiguous row
whose field count differs from the header's) still runs for every dataset regardless of whether that
dataset's schema is ever expected to have a footer at all. There is no per-dataset config signal
saying "this dataset has no footer, never treat a trailing mismatched row as excludable" -- so the
genuine LAST ROW of ANY file, at any size (not just sample-truncated files -- this is a materially
different and broader defect than CR-01/CR-04/WR-01's sample-truncation-boundary chain), is treated
as a candidate footer whenever it happens to look structurally malformed, and CR-03's content
re-validation "confirms" the exact same field-count-mismatch criterion against the real row,
excluding it via `_filtered_rows()`'s `continue` before it ever reaches ordinary per-row
`WRONG_COLUMN_COUNT` validation. Reproduced by the verifier three independent ways, most concretely
by running this project's own `generator/generate_csv.py` against `configs/datasets/customers.json`
(seed=11, 50 rows, 30% invalid ratio): the generator reports 50 rows (35 valid, 15 invalid) but
`process_chunks()` only accounts for 49 (35 valid, 14 invalid) -- one genuinely malformed
`wrong_column_count`-category row at the file's true end vanishes with zero trace in either stream.
Independently re-confirmed live during this planning session (see the exact `35/14/49` output this
plan's own investigation reproduced against the unmodified codebase).

**Fix:** Add an explicit, per-dataset opt-in config signal, `CsvDialectConfig.has_footer: bool =
False` (FTR-01) -- absent from every dataset config shipped today (`customers.json`/`orders.json`
both omit the `csv` block entirely and inherit `configs/defaults.json`'s, which gets an explicit
`"has_footer": false` added per this project's own established convention of listing every
`CsvDialectConfig` field's default explicitly). `prepare_source()`'s PASS 2 call site is the ONLY
place that changes: it now forces `footer_row_indices` to an empty set whenever
`config.csv.has_footer` is false, BEFORE building `excluded_indices` -- so a non-opted-in dataset's
`excluded_indices` never contains a footer candidate at all, and `_filtered_rows()`'s own signature,
body, and its CR-01 `_uncoverable_tail_indices()`/CR-03 content-re-validation/CR-04
coverage-eligibility machinery are completely UNMODIFIED by this plan. `detect/header.py` is also
completely unmodified -- it still always computes `footer_row_indices` via its unconditional
heuristic; only whether `source.py` CONSUMES that output is now conditional. `repeated_header_row_indices`
consumption is untouched and remains unconditionally active for every dataset regardless of
`has_footer` (explicitly out of scope per the gap-closure brief -- an exact-text match against the
real header is a much stronger, lower-false-positive signal that needs no opt-in gate).

**Why the two coverage gates are orthogonal, not conflicting (adversarial question addressed
explicitly):** when a dataset opts in (`has_footer=true`) and its ENTIRE file fits within the 64 KiB
detection sample (no truncation at all), `sample_was_truncated` is false, so
`sample_covered_row_count = len(sample_rows)` -- one past the last real row index. A genuine footer's
absolute index is always strictly less than that count, so `_uncoverable_tail_indices()`'s backward
walk (which starts at `idx = sample_covered_row_count`, a value the footer's own index can never
equal) immediately returns an empty set, imposing zero additional restriction -- the footer is
content-re-validated and excluded exactly as it always has been. This plan adds a new small-file,
opt-in, no-truncation test (`test_footer_optin_still_excludes_genuine_footer_row_within_sample`)
proving this exact case directly, alongside the five pre-existing, untouched 03-06..03-09 tests that
already prove the large-file/truncated case continues to work identically for opted-in datasets.

Purpose: Phase 4's Oracle bulk-loading builds directly on `process_chunks()`'s row counts and
per-row error classification -- this closes the last identified silent-data-loss vector on this path,
one that (unlike the four prior rounds) affects every dataset unconditionally today, not just files
exceeding the detection sample.
Output: `CsvDialectConfig.has_footer` (new opt-in field); `prepare_source()`'s gated
`footer_row_indices`/`excluded_indices` computation; three new regression tests proving the
default-off/opt-in-still-works/generator-driven-real-config behaviors; zero changes to
`detect/header.py` or to `_filtered_rows()`'s own body.
